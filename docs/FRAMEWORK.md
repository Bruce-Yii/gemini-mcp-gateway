## 1. 一句话

> 这是一个**单 owner、可自托管的 MCP 网关**：让只会调用已注册工具的 Web 客户端，通过 **3 个稳定工具** 和 **可替换执行底座**，真实、可靠、低成本地操作多个上游；用**离线评测 + 主动线上评测 + 被动线上评测**持续适配客户端和上游，最终降低主动评测成本，并把整套能力开源。

## 2. 六个模块（用户口径）

### 模块一：核心底座（可替换）

作用：

- 节省上下文；
- 多步骤执行；
- 跨上游工具调用。

候选实现：

- Code Mode（自由 JS 沙箱）；
- Typed Plan（类型化步骤）；
- Native（宿主原生工具调用）；
- Hybrid（按客户端/任务混合）；
- 未来可能出现更好的执行范式。

关键原则：

- **底座根据客户端替换**，不是全局唯一实现；
- 对客户端暴露的主接口仍是 3 工具；
- 底座替换不应改变读/写/授权/结果契约。

### 模块二：客户端

范围：

- Gemini、ChatGPT、Claude；
- 其他非 Code Mode 的 Web/客户端平台；
- Grok、Muse、Manus 等，如果存在同类 MCP 接入问题；
- 免费/会员计划可能影响自定义 MCP 权限，与是否免费无关。

内容：

- 客户端接入方法（已有 Gemini、ChatGPT 积累）；
- 客户端适配与优化；
- 客户端维度的主动/被动线上评测；
- 客户端接入也属于开源工程的一部分；
- 首次使用引导流程。

### 模块三：评测体系

三条线：

1. **离线/基准确认**
   - 早期复用成熟核心底座（如 Code Mode）；
   - 自己做过优化改进；
   - 按不同上游工具做官方/权威任务集的全覆盖离线评测与优化。

2. **客户端主动/被动线上评测**
   - 主动：人在真实客户端提问/探测；
   - 被动：真实线上 capture + 分析；
   - 客户端适配优化由它驱动。

3. **采集层**
   - session / project / task 交叉；
   - 支撑被动线上评测；
   - 主动/被动隔离评测；
   - 同一时间窗内主动 vs 被动对照；
   - 用主动评测反哺被动评测设计；
   - 目标：被动评测通过复现/分析逼近主动评测效果，减少主动频率、降低成本；
   - 包含自动化采集线。

### 模块四：上游接入

当前：

- GitHub、Notion、Linear、Vercel。

后续候选：

- Cloudflare、Gmail、Firecrawl、Exa、Tavily 等高频 MCP。

重点：

- **授权是第一位**：反复授权严重伤害体验；
- 不同上游接入方法不同；
- 首次使用引导流程；
- 上游接入也属于开源工程的一部分；
- 每个上游要有固定 SOP（接入、授权、评测、优化）。

### 模块五：运行时 / 部署

候选：

- Vercel（免费托管，当前较方便）；
- 同类免费托管平台（需调研，注意费用）；
- 内网穿透（Cloudflare 等；调研其他工具）；
- 本地部署（可能容器，注意是否过重）；
- 自有服务器。

原则：

- 按项目方式部署不能有扣费风险；
- 部署方式属于用户体验；
- 运行时与开源工程交叉。

### 模块六：开源工程

- 依赖前五层足够完整；
- 发布前问题多为成熟参照，优先级可后置；
- 可提前调研优秀项目开源治理；
- 包括客户端接入引导、上游接入引导、部署模板、许可证、安全、发布流程。

## 3. 分层与交叉关系（整理）

六个模块不是并列，也不是孤立。

### 3.1 用户旅程视角（上层）

```text
选择部署方式
  → 选择客户端（可能多个）
  → 选择上游（可能多个）
  → 首次接入/授权
  → 日常使用
  → 评测/优化
```

这引出上层问题：

- 一个网关、多客户端：如何隔离？
- 一个网关、多上游：如何隔离/限流？
- 多客户端并发、上游并发限制；
- 免费/付费计划差异；
- 多客户端下哪些能力底层复用。

### 3.2 分层视角

```text
场景层：部署 → 客户端 → 上游
  ↓
六模块：核心底座 / 客户端 / 评测 / 上游 / 运行时 / 开源
  ↓
横切层：授权、隔离、并发、采集、SOP、成本
  ↓
底层复用：执行底座、评测方法、认证框架、结果契约
```

### 3.3 交叉关系

| 交叉 | 说明 |
|---|---|
| 客户端 × 核心底座 | 底座按客户端替换 |
| 客户端 × 评测 | 每个客户端一条主动/被动评测 lane |
| 客户端 × 开源 | 接入引导、模板、限制说明 |
| 上游 × 评测 | 每个上游固定 SOP + 官方/权威任务集 |
| 上游 × 授权 | owner/refresh/static/DCR，体验第一位 |
| 运行时 × 客户端 | 多客户端隔离、并发 |
| 运行时 × 开源 | 部署模板、成本保护 |
| 评测 × 采集 | session/project/task 交叉，主动/被动隔离 |
| 开源 × 全部 | 依赖前五层成熟度 |

## 4. 主动 vs 被动线上评测（核心方法）

### 定义

- **主动线上评测**：
  - 人/agent 在真实客户端主动提问；
  - 真实环境、真实客户端；
  - 样本由人挑选，边界覆盖强，但不可重复、成本高。
- **被动线上评测**：
  - 采集真实线上会话；
  - 代表真实分布；
  - 缺 ground truth/用户意图，需要分析。
- **离线评测**：
  - 固定任务/官方集/回放；
  - 可重复、可进 CI，但不等于真实。

### 闭环

```text
主动线上评测
  → 发现新维度/高价值缺陷
  → 形成任务/回归
  → 被动线上采集 + 分析
  → 用主动结论校准被动规则
  → 被动评测逐步逼近主动效果
  → 降低主动评测频率与成本
```

### 关键要求

- 主动/被动必须**隔离统计**，不能混算；
- 同一时间窗可对照，但不跨构建硬比；
- 采集必须能关联 session/project/task/request；
- 主动结论要能回放到被动数据；
- 被动结论要能生成新的主动任务；
- 最终目标是**降低主动成本**，不是取消主动。

## 5. SOP（每个客户端/上游的固定方法）

### 客户端 SOP

1. 接入方式（OAuth/DCR/CIMD/手动）；
2. 工具 schema/profile/编码；
3. 计划/权限限制；
4. 主动评测任务；
5. 被动采集标签；
6. 适配优化；
7. 回归与文档。

### 上游 SOP

1. 传输/端点；
2. 授权方式与 owner；
3. 工具清单/allow-deny；
4. 官方/权威任务集；
5. 离线评测；
6. canonical/写路径；
7. 限流/并发/失败处理；
8. 文档与开源引导。

## 6. 部署与成本

- Vercel：当前方便，免费托管；注意函数时长/部署配额；
- 同类免费平台：需调研，避免扣费风险；
- Cloudflare 内网穿透：可用；调研其他隧道；
- 本地：容器可能过重，可作为可选；
- 服务器：自托管；
- 原则：**默认部署路径不能产生意外费用**。

## 8. 关键设计决策（当前）

1. 3 个稳定工具是主接口；核心底座可替换。
2. 执行器按客户端/能力选择，不全局唯一。
3. 客户端/上游都按 SOP 管理，不临时拼接。
4. 授权体验第一；网关独立 grant，不共享 DSH refresh token。
5. 主动/被动线上评测隔离，主动反哺被动。
6. 采集按 session/project/task 交叉。
7. 部署默认无扣费风险。
8. 开源依赖前五层，不提前公开半成品。
