## 1. 一句话

> 这是一个**单 owner、可自托管的 MCP 网关**：让只会调用已注册工具的 Web 客户端，通过 **3 个稳定工具** 和 **可替换执行底座**，真实、可靠、低成本地操作多个上游；用**离线评测 + 主动线上评测 + 被动线上评测**持续适配客户端和上游，最终降低主动评测成本，并把整套能力开源。

## 2. 六个模块（用户口径）

### 模块一：核心底座（可替换）

作用：

- 节省上下文；
- 多步骤执行；
- 跨上游工具调用。

候选实现：

- Code Mode（自由 JS 沙箱）；
- Typed Plan（类型化步骤）；
- Native（宿主原生工具调用）；
- Hybrid（按客户端/任务混合）；
- 未来可能出现更好的执行范式。

关键原则：

- **底座根据客户端替换**，不是全局唯一实现；
- 对客户端暴露的主接口仍是 3 工具；
- 底座替换不应改变读/写/授权/结果契约。

### 模块二：客户端

范围：

- Gemini、ChatGPT、Claude；
- 其他非 Code Mode 的 Web/客户端平台；
- Grok、Muse、Manus 等，如果存在同类 MCP 接入问题；
- 免费/会员计划可能影响自定义 MCP 权限，与是否免费无关。

内容：

- 客户端接入方法（已有 Gemini、ChatGPT 积累）；
- 客户端适配与优化；
- 客户端维度的主动/被动线上评测；
- 客户端接入也属于开源工程的一部分；
- 首次使用引导流程。

### 模块三：评测体系

三条线：

1. **离线/基准确认**
   - 早期复用成熟核心底座（如 Code Mode）；
   - 自己做过优化改进；
   - 按不同上游工具做官方/权威任务集的全覆盖离线评测与优化。

2. **客户端主动/被动线上评测**
   - 主动：人在真实客户端提问/探测；
   - 被动：真实线上 capture + 分析；
   - 客户端适配优化由它驱动。

3. **采集层**
   - session / project / task 交叉；
   - 支撑被动线上评测；
   - 主动/被动隔离评测；
   - 同一时间窗内主动 vs 被动对照；
   - 用主动评测反哺被动评测设计；
   - 目标：被动评测通过复现/分析逼近主动评测效果，减少主动频率、降低成本；
   - 包含自动化采集线。

### 模块四：上游接入

当前：

- GitHub、Notion、Linear、Vercel。

后续候选：

- Cloudflare、Gmail、Firecrawl、Exa、Tavily 等高频 MCP。

重点：

- **授权是第一位**：反复授权严重伤害体验；
- 不同上游接入方法不同；
- 首次使用引导流程；
- 上游接入也属于开源工程的一部分；
- 每个上游要有固定 SOP（接入、授权、评测、优化）。

### 模块五：运行时 / 部署

候选：

- Vercel（免费托管，当前较方便）；
- 同类免费托管平台（需调研，注意费用）；
- 内网穿透（Cloudflare 等；调研其他工具）；
- 本地部署（可能容器，注意是否过重）；
- 自有服务器。

原则：

- 按项目方式部署不能有扣费风险；
- 部署方式属于用户体验；
- 运行时与开源工程交叉。

### 模块六：开源工程

- 依赖前五层足够完整；
- 发布前问题多为成熟参照，优先级可后置；
- 可提前调研优秀项目开源治理；
- 包括客户端接入引导、上游接入引导、部署模板、许可证、安全、发布流程。

## 4. 主动 vs 被动线上评测（核心方法）

### 定义

- **主动线上评测**：
  - 人/agent 在真实客户端主动提问；
  - 真实环境、真实客户端；
  - 样本由人挑选，边界覆盖强，但不可重复、成本高。
- **被动线上评测**：
  - 采集真实线上会话；
  - 代表真实分布；
  - 缺 ground truth/用户意图，需要分析。
- **离线评测**：
  - 固定任务/官方集/回放；
  - 可重复、可进 CI，但不等于真实。

### 闭环

```text
主动线上评测
  → 发现新维度/高价值缺陷
  → 形成任务/回归
  → 被动线上采集 + 分析
  → 用主动结论校准被动规则
  → 被动评测逐步逼近主动效果
  → 降低主动评测频率与成本
```

### 关键要求

- 主动/被动必须**隔离统计**，不能混算；
- 同一时间窗可对照，但不跨构建硬比；
- 采集必须能关联 session/project/task/request；
- 主动结论要能回放到被动数据；
- 被动结论要能生成新的主动任务；
- 最终目标是**逐渐减少主动评测频率、降低主动评测成本**，同时优化整个闭环；原文没有主张取消主动。

## 8. 关键设计决策（当前）

1. 3 个稳定工具是主接口；核心底座可替换。
2. 执行器按客户端/能力选择，不全局唯一。
3. 客户端/上游都按 SOP 管理，不临时拼接。
4. 授权体验第一；网关独立 grant，不共享外部宿主导入的 refresh token（DSH 只是当前外部导入源，不是产品模块）。
5. 主动/被动线上评测隔离，主动反哺被动。
6. 采集按 session/project/task 交叉。
7. 部署默认无扣费风险。
8. 开源依赖前五层，不提前公开半成品。

## 11. 客户端模式纠正（2026-11-24）

“非 Code Mode 的 Web/客户端”应准确写成：

- **客户端的非代码模式**，不是“非 Code Mode 架构的客户端”；
- 例：Claude 有 Code 模式，也有网页端非代码模式；Codex 可能对 MCP 做过处理；
- 观察重点：**网页端非代码模式基本没做 MCP 优化**；
- 因此客户端不能只按品牌分类，必须按 **平台 × 模式 × MCP 能力** 分类。

### 客户端能力矩阵

| 维度 | 取值 |
|---|---|
| 平台 | Gemini / ChatGPT / Claude / Grok / Muse / Manus / 其他 |
| 模式 | 网页聊天 / 桌面 / IDE / CLI / Code 模式 |
| MCP 能力 | 未支持 / 只读 / 读写 / 工具搜索 / 代码编排 |
| 认证 | OAuth / DCR / CIMD / 手动 / 无 |
| 计划 | 免费 / 会员 / 企业 |
| 工具面 | 固定 / 可发现 / 可编排 |

> 同一品牌不同模式，能力可能完全不同；适配与评测必须按“模式”分 lane，不能按品牌一刀切。

### 对架构的直接含义

1. 客户端适配层需要 **mode detection**，不能只 detect 品牌；
2. 非代码 Web 模式是网关 Code Mode 的主要价值场景；
3. 已有 Code 模式的客户端，网关可能是冗余/补充，需要单独策略；
4. 评测必须按“平台 × 模式”分账，不能把 Code 模式和网页模式混算。

## 12. 原框架的遗漏（补充）

1. **执行所有权**：Code Mode 在网关侧，但客户端可能有自己的 agent/tool loop；需要明确谁规划、谁执行、谁负责上下文。
2. **状态与隔离模型**：client instance / session / project / task / OAuth grant 的作用域；单 owner 不等于单客户端。
3. **并发与限流**：多客户端并发、上游并发/配额、sandbox 配额；需要调度器/队列/背压。
4. **客户端能力协商**：模式、MCP 能力、计划权限无法可靠自动检测时的 fallback。
5. **评测的 ground truth/标注层**：被动线上分析缺用户意图和标准答案；需要标注、抽样、偏差控制。
6. **主动/被动采样偏差**：主动任务是人挑的，不代表真实分布；被动 capture 不代表边界；需要校准。
7. **上下文预算策略**：截断/摘要/结果表示是横切策略，不只在核心底座。
8. **信任与安全边界**：client OAuth、upstream grant、sandbox、secret、capture 存储，需要横切模型。
9. **成本模型**：token、上游 API 配额、部署、存储；免费平台不能有扣费风险。
10. **协议/版本兼容**：MCP 版本、客户端能力、工具面版本（/mcp/v2）。
11. **产品 onboarding 顺序**：部署 → 上游授权 → 客户端连接，可能不是用户自然的“部署→客户端→上游”。
12. **开源治理**：许可证、安全披露、兼容策略、贡献流程，不能只当发布尾巴。
13. **评测自身质量**：基准污染、过拟合、主动任务选择偏差、被动日志缺意图。
14. **canary/shadow/回滚**：线上评测到发布之间的发布工程。

## 13. 2026-11-24 用户纠正后的定稿

### 13.1 客户端

- 目标就是 **网页端非代码模式**：客户端不能自己跑代码，MCP 优化不足；
- 不是按品牌抽象一堆“能力矩阵”，而是：
  **客户端 × MCP 设计 × 非代码模式**，逐个平台做：
  - Gemini
  - ChatGPT
  - Claude
  - 后续同类平台
- 每个平台都走：接入 → 测试 → 优化 → 评测 → 回归。
- Code 模式客户端（Claude Code/Codex 等）不是当前主战场；只作为后续兼容对象。

### 13.2 主动 vs 被动线上评测

- **主动线上评测 > 被动线上评测**（在当前项目语境下）。
- 主动有明确任务/预期，能打到被动覆盖不到的地方；
- 被动有真实分布，能发现主动没覆盖的地方；
- 两者有交集；主动发现的新维度可以倒推优化被动设计；
- 目标：用主动反哺被动，降低主动频率和成本，不是取消主动。

### 13.3 “ground truth” 的正确含义

MCP 网关评的是**工具调用**，不是模型思考。

- 不评“用户意图/模型推理质量”；
- 评工具层面：
  - 参数是否符合契约；
  - 返回是否符合预期 schema/字段/字节；
  - 上游真实结果是否一致；
  - 写后副作用是否正确；
  - 同 args 重放是否一致。
- 被动 capture 没有“任务预期”，但可以用：
  - 同调用重放对比；
  - 上游 API 直接核验；
  - schema/契约断言；
  - 主动任务标签回填；
  - 已知 fixture 对照。
- 所以“被动没有 ground truth”应改为：
  **被动缺少任务级预期，但有工具级可核验真值。**

### 13.4 上下文预算

- 属于核心底座的细分设计，不单独成模块。

### 13.5 配额/成本

- token 成本由上下文节省解决，是核心价值；
- 上游配额是上游/用户的事，但 **Firecrawl/Exa 等搜索 API 的浪费调用**可以优化：
  - 去重/缓存；
  - 查询预算；
  - 结果裁剪；
  - 调用合并。
- 存储成本先不作为独立架构层。

### 13.6 多客户端

- 单 owner 但多客户端；需要考虑：
  - 客户端级作用域；
  - 上游 grant 共享/隔离；
  - 网关并发（上游并发限制主要由上游决定）；
  - capture 标签。

### 13.7 不引入的东西

- 暂不引入 canary/shadow/复杂发布工程：先把真实客户端/写回环/授权做通；
- 暂不做通用“客户端能力检测框架”：逐个平台实测优先；
- 暂不把安全/成本/真值做成独立模块，先作为实现约束。

## 14. 审批 / 权限（2026-11-24 深挖）

### 用户反馈

- 调研 MCP 的人普遍讨厌审批；
- 客户端 MCP 管理界面本来有“每次询问 / 允许”的权限选择；
- Gemini 已设成允许，仍经常弹窗；
- 需要判断：是网关问题，还是 Gemini 设计问题。

### 代码事实

当前 3 工具 annotations：

| 工具 | readOnlyHint | destructiveHint | openWorldHint |
|---|---|---|---|
| search | true | false | false |
| execute_read | true | false | **true** |
| execute | false | **true** | **true** |

Google/Gemini 的规则（公开资料 + 社区实测）：

- `destructiveHint` 和 `openWorldHint` 会触发确认；
- 没有 `readOnlyHint` 的工具被视为可能 destructive；
- 因此即使“允许”，destructive/openWorld 仍可能强制确认，属于客户端策略。

### 初步判断

1. **不是纯 Gemini 设计问题**：我们的 annotations 主动声明了 destructive/openWorld；
2. **也不是纯网关 bug**：声明本身语义上没错，`execute` 确实可写、可访问外部；
3. **双重触发**：
   - `execute_read` 的 `openWorldHint:true` 也可能触发确认；
   - `execute` 的 `destructiveHint:true` 更会触发；
4. **网关内部 approve 不是客户端弹窗的直接原因**，但如果模型因 gateway 拒绝写而重试，可能触发更多次客户端确认。

### 设计原则

- 客户端权限设置是**用户意图的第一权威**；
- 网关不应再叠加“用户审批”，最多做代码级 dryRun/approve 安全闸；
- 不要用 annotations 伪装安全；
- 但可以通过 profile 精准降低无意义弹窗。

### 可选方案

A. 保持诚实 annotations，接受写操作确认；只读也可能因 openWorld 弹窗。
B. 对 Gemini profile 调整 annotations：
   - `execute_read`: openWorldHint=false；
   - `execute`: destructiveHint=false, openWorldHint=false；
   - 风险：under-declare，客户端不再警告写/外部访问。
C. 拆分 write 工具：破坏 3 工具不变量，暂不考虑。
D. 网关内部把客户端已发起的 execute 视为 host approval，减少模型重试；客户端弹窗仍由 annotations 决定。

**建议**：先做 B 的**实验 profile**（不改默认、不改 ChatGPT/Claude），在真实 Gemini 窗口验证弹窗变化；同时做 D，避免网关重试叠加确认。不要在未验证前全局改 annotations。

### 待验证

- Gemini web 自定义 MCP 是否真的忽略“允许”对 destructive/openWorld 工具？
- `execute_read` 单独改 openWorldHint=false 是否减少只读弹窗？
- `execute` 改 destructive/openWorld 后，客户端是否仍弹？
- 真实任务中一次写操作平均触发几次确认？

### 原则

- 审批是客户端 UX，不是网关功能；
- 网关只保留代码级安全闸；
- 不让用户为“读”审批；
- 写操作可以少弹，但不能靠撒谎 annotations 实现；先实验 profile，再决定全局策略。

## 16. 术语纠正：DSH 不是产品模块

- 用户原始框架里没有 DSH；
- DSH 是当前开发宿主/凭据来源，属于实现迁移细节；
- 之前授权反复失效，根因是网关与 DSH 共享 rotating refresh token；
- 目标架构不应把 DSH 当成 owner 类型；产品层 owner 只应有：
  - gateway-owned（网关自己的 grant）
  - manual static（用户创建的长期 token）
  - external-imported（外部导入，legacy，只读，不 refresh）
- 代码里的 owner=dsh 只是当前迁移兼容值，不应出现在完全态架构；
- 产品目标不是“不顶 DSH”，而是“网关授权独立、可预期、不反复失效”。

## 17. 主动 ↔ 被动关联机制（修正第六点）

第六点现实不是“对不上”，而是“能对，但靠人眼、麻烦”：

- 用户每次主动提问，都会把反馈发到开发窗口；
- 开发窗口/台账有真实时间戳；
- 被动 capture 也有时间戳；
- 理论上可按时间、平台、任务对齐，但缺少标准字段和自动关联，容易漏/错。

设计目标：用户零额外操作；开发窗口只记一条标准记录；被动 capture 自动；关联脚本输出 exact/likely/weak/unmatched；对不上写原因，不硬配。

### 最小机制

1. 主动侧：`active-eval.v1`
   - activeEvalId、平台、模式、项目、prompt、taskFingerprint、startedAt/endedAt、expected、observed、来源窗口/台账；
2. 被动侧：capture 已有 requestId/session/platform/project/时间；补 clientMode、taskId；
3. 关联：`link-active-passive`
   - exact：taskId/activeEvalId；
   - likely：时间窗 + 平台 + 项目 + 工具序列指纹；
   - weak：只有时间/平台；
   - unmatched：写原因；
4. 主动标签回填被动；主动规则反哺被动检查器；统计一致率后再降低主动频率。

详见：[docs/eval/ACTIVE-PASSIVE-CORRELATION.md](eval/ACTIVE-PASSIVE-CORRELATION.md)

### 边界

- 不编造 requestId；
- 不把 unmatched 当 pass；
- 不跨构建硬比；
- 主动记录时间用真实消息时间/UTC；
- 被动 capture 不为主动记录改变。
