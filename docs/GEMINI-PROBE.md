# Gemini 网页端体感探针（手动跑）

> 用途：Gemini 网页端没有工具调用日志、没有 token 用量，体感反馈是唯一的一线数据。
> 本文件给 lead 准备**可直接复制的任务序列 + 提问脚本**；跑完把 Gemini 的回答原样贴回会话即可，不需要你整理。
>
> 任务来源：风格参照 `explore/tasks-v2.json` 里 105 条官方逐字 prompt，但去掉了占位符数据
> （`octocat/Hello-World`、`#123`、`abc1234` 这类在真实账号里必然 404），改成"我"的真实账号任务；
> 同时刻意覆盖：search 发现、select 取 schema、大结果沙箱过滤、跨服务编排、读写判断、无法完成时的拒绝。
>
> 版本：2026-11-22。线上运行时以 `https://gemini-mcp-gateway-yu-ac3a.vercel.app/healthz` 的 commit 为准，
> 贴回来时附上更好；没有也能跑。

## 怎么跑

- 开 **2 个新对话**（避免上下文串味），每条任务跑完再发下一条。
- **Gemini 侧单轮工具调用有上限**（2026-11-22 实测：约 20 次调用后报"本轮工具调用次数配额已用尽"，不是网关限制）。一个对话最多放 8-10 条任务，跑完开新对话。
- 每个对话最后粘贴文末的「问 Gemini 的问题」。
- 把每个对话的**完整最终回答**（含它提到的工具名、报错原文）原样贴回来。
- 第 8 条是写操作探测，**不要真的执行**，只让它说明计划。
- 时间紧的最小版本：对话 1 的第 1、3 条 + 问题 1、3、7。

## 对话 1：单服务读取 + 工具发现

1. 列出我 GitHub 最近更新的 5 个仓库，并给出每个仓库最近一次提交的时间和提交说明。
2. 在 Notion 里搜索标题包含「项目」或「Project」的页面，返回前 5 个以及它们的最后编辑时间。
3. 列出分配给我的 Linear issue 中状态不是 Completed 的最新 5 条，给出标题、状态和更新时间。
4. 列出我在 Vercel 上最近的 3 个部署，给出项目名、状态、commit sha 和创建时间。

## 对话 2：跨服务 + 大结果 + 边界 + 读写判断

5. 查一下我 Vercel 上最近一个失败的部署，找到它的 commit sha，再用 GitHub 查这个 commit 的提交信息，用三行汇总。
6. 从我 GitHub 最近有提交的仓库里挑一个，读它的 README 全文，压缩成 5 条要点，不要贴原文。
7. 把我在 Notion 里标题包含「项目」的第一个页面的完整内容取出来，统计大概字数，并给出 3 条下一步行动项。
8. 如果我现在让你在 GitHub 上给一个仓库创建一个标题为「MCP smoke test」的 issue：先不要真的执行，告诉我你会调用哪个工具、参数是什么、需不需要我确认。

## 问 Gemini 的问题（每个对话最后粘贴这段）

刚才是真实的 MCP 网关使用测试。请按下面 8 个问题如实回答，说具体任务、工具名和原始报错，不要客套：

1. 每条任务你是怎么找到工具的？`search` 里输入了什么关键词？几次找到？
2. 有没有 search 返回的工具不对/不够、需要再搜或者干脆放弃？是哪条任务？
3. 有没有参数填错后重试？具体是哪个字段、什么类型的错？
4. `select:<name>` 返回的 schema 是否太长、或者关键参数看不懂？哪个工具？
5. `execute_read` 和 `execute` 的区分清楚吗？你更常用哪个，为什么？
6. 返回结果有没有被截断、或者太长到挤占上下文？举一个具体例子。
7. 按 1-5 分评价四项：找工具 / 写代码 / 结果可读性 / 省上下文感受。
8. 如果只能改一件事，你改哪件？只说一件。
9. 有没有因为返回字段名和预期不一致（比如以为是 `state.name`，实际是 `status`）而先探字段、多花调用？哪个工具、几次？

## 追问：对话 1 第 4 条（Vercel 部署返回空）

把下面整段粘给同一个对话；只要原始返回，不要总结：

```text
第 4 条 Vercel 部署返回了空数组，先别下结论，按顺序执行并贴原始返回：
1. 调 vercel__list_deployments({ limit: 3 })，不带 teamId，贴出原始返回。
2. 调 vercel__list_projects()，贴出你看到的项目和 projectId。
3. 如果第 1 步还是空：用第 2 步任一 projectId 调 vercel__list_deployments({ projectId, limit: 3 })，贴原始返回。
4. 你之前传的 teamId（team_...）是从哪个工具拿到的？再调一次 vercel__get_git_deployment_context，贴出你看到的 team 列表。
5. 任何一步如果报错，把错误原文一起贴出来。
```

## 回收后的处理（lead 侧）

- 按台账四步归类：表象 → L1 直接原因 → L2 设计决策 → L3 认知/假设，再横向找同类、写收益与副作用、走一步看三步。
- 能复测的转成 `explore/` 任务或 `tests/` 回归；不能复测的登记为 DEC 或已知。
- **不把 Gemini 建议直接当工单**：历史上出现过 toolCalls 回显（建议截断，实际应从模型上下文里根本不发）、
  `services()` online（建议显示状态，实际制造虚假安全感）、描述过长（建议截断，实际病根是 BM25 把描述当检索信号）
  这类"问题对、解法不是最优"的情况。先归因，再决定动不动。
