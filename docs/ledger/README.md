# 优化台账（Ledger）

> 所有工作按 **分类** × **批次** 记录。三阶段门控：**前一项通过才进下一项**。
> 阶段一：测评场景覆盖全且权威 → 阶段二：暴露问题逐条追溯根源并修复（一层层往上查）→ 阶段三：全部优化后全量重测。

## 分类

| 分类 | 代号 | 含义 |
|---|---|---|
| 测评场景 | `SCENARIO` | 任务集覆盖、来源权威性 |
| 问题 | `ISSUE` | 暴露的缺陷/短板 |
| 根因 | `ROOT` | 一层层往上查得到的根本原因 |
| 优化 | `FIX` | 针对根因的改动 |
| 测试 | `TEST` | 验证结果 |
| 决策 | `DEC` | 做/不做的权衡 |

## 门控规则

- B1 不通过 → 不进 B2；B2 不通过 → 不进 B3
- 每项结论必须有证据（文件/测试/命令输出），不凭记忆、不靠自述
- "权威"的定义：官方逐字 prompt ≥ 权威 benchmark prompt ≥ schema 驱动+反向验证（逐级降权，如实标注）

## 证据规则（防再犯，RC-F lead 认知 L3 制度化）

> 来源：B2 根因追溯 RC-F —— Firecrawl 额度误判、Cloudflare normalize 误判、部署 runtime 非法三类 lead 自身错误的共同 L3 是
> "有权威依据可支配却没去用"。以下三条写死为证据规则，不靠记忆、不靠自述；任一违反，则该项结论不成立，不能进下一批次。

1. **额度/配额结论必须逐个 key 实测并附时间戳**。不得凭搜索摘要、缓存文案或他人转述断言"某 key 有/没有额度"；
   每次结论记录实测时间（含时区）与逐 key 结果。（Firecrawl 误判根因）
2. **技术结论必须逐文件读源码 + 交叉验证产物**。断言"某 SDK 有某函数 / 某行为"前，逐文件读源码并对照构建产物、
   测试输出或类型定义；不得从搜索摘要、错误文案或二手文档间接推断。（Cloudflare normalize 误判根因）
3. **配置改动后必须跑校验**。改 `config*.json` / `vercel.json` / 环境变量后，跑 schema/config 校验或 `vercel build` 干跑，
   确认无非法字段再交付；不得只改文件就宣称完成。（非法 runtime 字段导致部署 ERROR 根因）

> 这三条是上面门控规则"每项结论必须有证据"的可操作细化。详见 `batch-2-rootcause.md` RC-F。
