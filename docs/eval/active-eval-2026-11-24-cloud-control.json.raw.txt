### 3. 专项评估：Token 节省、多任务效率与核心优势

#### (1) 上下文 Token 真的省很多吗？

* **结论：实测省得非常明显，是这个网关最直接的结构性收益。**
* **实测依据**：目前 4 个在线服务合计 **189 个工具**（Notion 恢复后 200+）。如果原生直连，每轮对话都要把近 200 个 JSON Schema 塞进系统上下文，长会话很快就会被工具定义吃掉大量窗口，且模型选工具准确率会下降。网关把它们压缩成 **3 个入口工具**（`search`、`execute_read`、`execute`），让我们这个窗口能连续完成十几个 PR 的深度代码审计、写文档和合代码，撑了非常多轮才触发一次上下文压缩。
* **扣分项**：省下的 Token 会在两种情况下被“倒扣”——一是脚本没在沙箱里过滤直接吐原始大 JSON（触发 ~20KB 截断后反复重读）；二是 `execute_read` 描述过长导致漏用 `sliceLines`。把这两点收紧，省 Token 效果还能再提一档。

#### (2) 多任务效率真的提升了吗？

* **结论：提升极大，实际价值甚至高于省 Token。**
* **实测依据**：以前做一次跨模块排查（同时看 4 个源码文件 + 查 PR diff + 查 Vercel 部署 + 查 Linear 团队），原生 MCP 至少需要 6–8 轮串行模型往返，每轮都要等推理、重新吞吐历史上下文、还要点多次审批确认。用网关的 `execute_read`，**1 轮沙箱脚本就能并发拉完所有跨平台数据并做好聚合裁剪**，把多轮往返压成 1 轮，审批打断次数也成倍下降。
* **扣分项**：遇到 `BC-011/012/013/017`（如 `Promise.all` 单条 404 拖垮整批、嵌套格式不统一）时会多耗 1–2 轮容错重试；这些都属于代码层可根治的毛刺。

#### (3) 其他明显优势

* **多客户端一次配置、统一复用**：Gemini、ChatGPT（及后续 Claude / Codex）共用同一套网关和上游 OAuth/PAT，不用在每个客户端重复接 5 套 MCP 和反复授权。
* **读写物理隔离 + 统一安全门**：`execute_read` 与 `execute` 天然拆开，方便客户端对只读静默放行、对写入严格审批；入站还有 `OAUTH_APPROVE_PASSPHRASE` 兜底。
* **自带可观测性与自进化闭环**：直连第三方 MCP 是黑盒，踩坑没法量化；网关通过 R2 全量采集 + 4 维分账（平台/协议/配置/版本）+ 主被动对照，能把每次真实踩坑沉淀成回归用例。
* **统一的上游脏接口适配层**：官方 MCP 质量参差不齐，网关能在 `codemode` 层统一做解包、分页、截断保护与字段归一化，一处修复全客户端受益。
