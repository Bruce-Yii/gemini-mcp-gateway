### 2. 有没有因为工具描述太长或没写清导致漏用内置能力？

**有，而且很明显。** `execute` / `execute_read` 的工具描述是一整段接近 1,500 词、没有分段排版的纯文本大长文：

1. **漏用 `codemode.sliceLines` / `readFileRange**`：虽然描述里写了 `sliceLines` 和 `readFileRange`，但因为大段文字里混杂了冷启动状态、Batch 11、GitHub Actions、Truncation 等十几个主题，写脚本时我下意识还是用原生 JS `text.split("\n").slice(...)`，没调用内置 `sliceLines`。
2. **误用 `grepSnippet` 的 `window` 参数**：描述只写了 `grepSnippet(text, keyword, window)`，没写清 `window` 是**字符数**且有最小值/默认钳位，导致传入 `15` 后得到无用的 20 字符窗口。
3. **没有用 `codemode.applyFilePatch**`：多文件修改时直接用 `github__get_file_contents` + JS `replace` + `github__create_or_update_file` / `github__push_files`，因为描述里 `applyFilePatch` 提到的 `patch` 格式没有给出具体示例（unified diff 还是 `{old, new}`），不如自己 `string.replace` 确定。

### 3. 返回结果：哪些冗余撑上下文，哪些关键字段缺失？

* **冗余撑上下文的字段**：
1. `waitForPrChecks` 的 `checkRuns[]`：哪怕只需要看状态，每条也带了完整 `html_url`、`details_url`、`started_at`、`completed_at`；我每次在返回前都手动 `.map(r => ({ name, status, conclusion, id }))` 裁剪。
2. `github__create_or_update_file` / `github__push_files`：会返回整段 `content` 元数据、完整 author/committer/parents 对象，实际我只需要 `commit.sha` 和 `html_url`。
3. `github_actions_get_job_logs`：一旦直接返回就是全量兆字节级日志，必须自己在沙箱里截断和过滤。


* **缺失导致额外多查一轮的关键字段**：
1. `waitForPrChecks` **顶层缺 `runId**`：失败后想调 `github_actions_list_workflow_jobs({ run_id })` 必须从 `checkRuns[0].html_url` 里肉眼/正则拆出 `45303891167`。
2. `waitForPrChecks` / `github_actions_*` **缺失败步骤与失败摘要提取**：没有把失败 job 对应的 `failedStep` 和日志里匹配 `✖ ` / `Error:` / `##[error]` 的片段一并返回，导致每次 CI 红了都要「先看 checkRuns → 再查 logs → 再写正则过滤」多走 1–2 轮。
3. **缺 GitHub Actions Run Annotations / Check Suite 错误摘要**：当 `steps: []` 且日志 404（例如私有库额度耗尽、workflow 语法/权限拒绝）时，目前没有任何助手能取回 GitHub 页面顶部的错误横幅。

### 4. 宿主体验：弹窗频率、响应速度与稳定性

* **审批弹窗频率**：`execute_read`（只读）和 `execute`（写操作）拆分得比较合理。查文件、查 CI、看日志走 `execute_read` 基本无打扰；改文件、建分支、提 PR、合并走 `execute` 才触发写入，整体频率可控。
* **响应速度**：单次 `execute_read` / `execute` 很快（通常 1–3 秒内完成）；但 `waitForPrChecks` 在等 4–5 分钟的 CI 时，单次 28 秒轮询窗口注定超时返回 `in_progress`，还是得依赖你回「继续」再查。
* **多步连续调用稳定性**：
* 沙箱内部连续执行多步 GitHub API（例如一个 `execute` 里连续做 `createBranchIfMissing` → `get_file_contents` → `push_files` → `create_pull_request`，8–10 个动作打包成 1 轮）**非常稳**，原子 `push_files` 一次性推 5 个文件没出现过并发冲突。
* **主要不稳定点在宿主侧 MCP 挂载生命周期**：对话空闲或跨一段时间后，出现过一次连接直接掉线（`unknown tool name` 且 `expand_tools` 返回 `not-found`），需要用户手动 `@Gemini Mcp Gateway` 才能重新挂上。

### 5. Top 5 高 ROI 改进清单（按投入产出比从高到低）与版本对比

#### Top 5 改进清单

1. **新增/增强 `waitForPrChecks` 或 `github_actions_diagnose_failure` 一键诊断失败（ROI 最高）**
* **具体改法**：在 `waitForPrChecks` 返回里直接加上顶层 `runId`；并在存在失败 Job 时（或提供 `diagnoseFailedCheck({ owner, repo, pullNumber })`），自动拉取失败 Job 的 `failedSteps`、Check Run `annotations`（解决 `steps: []` / 日志 404 问题），并用内置正则（`✖ `、`AssertionError`、`Error:`、`##[error]`、`SQLSTATE`）过滤掉 `docker rm` / `checkpoint` 噪音，返回精准的 50 行故障上下文。
* **预期收益**：每次修 CI 红灯可省下 **1–2 轮**「捞失败步骤 → 过滤日志尾部噪音」的来回。


2. **修复网关空闲掉线 / 支持 `expand_tools` 自动重连**
* **具体改法**：当 `custom_mcp__*` 工具在会话中已声明过但通道断开时，宿主在 `expand_tools` 或工具路由层自动重拉 MCP 进程，而不是直接返回 `not-found` 逼用户手动 `@Gemini Mcp Gateway`。
* **预期收益**：消除对话中断，每次掉线省下 **1 轮人工唤醒**。


3. **升级 `grepSnippet` 支持按「行」切片，且默认窗口改大**
* **具体改法**：给 `grepSnippet` 增加 `{ unit: 'lines' | 'chars', before, after }`（或直接默认按行取前后 15 行），并在 `execute_read` 接近 20KB 截断阈值时，给出具体的截断字段名和行号提示。
* **预期收益**：读长代码文件（如 `ci.yml`、`0001_init.sql`、`run-eval-v2.mjs`）时省下 **1–2 轮**补读切片。


4. **把 `execute` / `execute_read` 工具描述精简并结构化（加示例、删重复）**
* **具体改法**：现在一段 1,500 词里有不少重复规则（比如 `unwrapBatch`、`Truncation`、`Batch contract` 各自重复讲了两遍）；压缩到 400 词以内分节列出，给 `applyFilePatch` 和 `grepSnippet` 各补 1 行真实参数示例。
* **预期收益**：减少每次上下文 Token 占用，并让内置 helper 的实际命中率明显提高。


5. **给 `waitForPrChecks` / 常用多文件读提供更明确的批处理默认保护**
* **具体改法**：在文档首行用加粗提示「多文件读取优先 `safeAll`，不要用 `Promise.all`」，或提供 `readRepoFiles({ owner, repo, ref, paths })` 一次返回 `{ path, sha, content, error }`，单文件 404 不炸整批、超长文件自动带行号范围。
* **预期收益**：避免因单个路径猜错导致整批并发读作废，省下 **1 轮重试**。



#### 与之前版本的直观对比

* **明显变好的地方**：
* `fileResult(r).content` 终于彻底干掉了之前烦人的 `successfully downloaded text file (SHA: ...)\n` 前缀，拿出来就能直接改直接推，零清洗成本；
* `github__get_file_contents` 的 `ref` 参数行为对齐了，不再和 `branch` 打架；
* `github__push_files` 单次原子提交多个文件非常丝滑（这次 PR #106 一次推 5 个文件、PR #107 一次推 3 个文件零失误）；
* `waitForPrChecks` 和 `github_actions_*` 助手把原本需要自己拼 4–5 个 GitHub REST 请求的流程压缩成了一次调用。


* **变差或新暴露的短板**：
* 工具描述随着功能堆叠变得越来越长、越来越像补丁合集（同一条规则重复出现），反而不利快速检索 helper 用法；
* `execute_read` 的截断阈值对多字段返回偏保守，遇到大 SQL/YAML 文件很容易连环截断。
