# **M4 Gate 5 跨客户端 A/B 测试总结**

### **一、测试目的**

本次 A/B 测试旨在对比两种 MCP 工具接入方式在 ChatGPT 环境中的实际表现：

- **A 组：Direct MCP**，通过 ChatGPT 原生连接器直接调用 GitHub、Vercel、Linear、Notion、Figma。
- **B 组：MCP Gateway**，通过 Gateway 的 Code Mode 统一发现和调用上述服务。

两组使用相同的权威测试套件，执行相同的只读任务，重点验证工具发现、Schema 加载、文件读取、跨服务调用和执行可靠性。

核心问题是：**相比直接使用连接器，增加一层 MCP Gateway 是否能带来实际优势？**

### **二、测试结果**

两组都能完成主要测试任务，但表现出不同特点：

- **Direct MCP**：可以直接使用 ChatGPT 原生连接器完成跨服务调用，不需要额外经过 Gateway。
- **MCP Gateway**：具备统一工具发现、Code Mode、多步骤调用和结果标准化能力。其中，文件读取结果规范化是本次测试中比较明确的局部优势。

但从整体表现看，Gateway 没有体现出明显的效率优势。两组在工具按需加载和多步骤编排方面也存在能力重叠。

### **三、核心发现**

本次测试最重要的发现是：**ChatGPT 原生环境已经具备 Gateway 原本希望解决的两项核心能力。**

1. **按需加载**：ChatGPT 原生工具机制已经能够按需发现和使用工具，Gateway 在减少上下文占用方面尚未体现额外优势。
2. **多步骤编排**：ChatGPT 本身能够完成多工具调用、并行查询、串行依赖和结果整合，Gateway 的 Code Mode 没有证明能进一步改善这一过程。

因此，Gateway 原本的两项核心价值主张，在 ChatGPT 环境中与宿主自身能力产生了明显重叠。

### **四、初步结论**

本次 A/B 测试并没有证明 MCP Gateway 在 ChatGPT 环境中优于 Direct MCP。

两种方式的主要区别在于：

- Direct MCP：依赖 ChatGPT 原生连接器体系，直接使用工具。
- MCP Gateway：在 ChatGPT 与 MCP 服务之间增加统一的工具接入和执行层。

Gateway 仍然具有跨客户端复用、统一权限治理、执行审计、返回值标准化等潜在价值，但这些优势尚未通过本次测试得到充分验证。

**最终判断：在 ChatGPT 这个已经具备原生工具发现和多步骤编排能力的环境中，Gateway 的增量价值目前并不明显。它是否值得引入，关键取决于能否在跨客户端复用、治理、可靠性和可观测性方面提供 Direct MCP 无法提供的能力。**

本次结果属于当前测试场景下的初步判断，不代表 Gateway 在其他客户端或模型环境中也没有优势。
