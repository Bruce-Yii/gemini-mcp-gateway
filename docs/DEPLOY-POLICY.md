# Deployment policy — 不频繁，但要灵活

> 目标不是“每天最多几次”，而是：
> **没有值得部署的进展就不部署；有明确进展或必须实测时，就部署。**
> 100/day 是平台上限，不是配额目标。

## 1. 什么时候不部署

- 纯文档、README、AGENTS、ledger、eval 报告；
- 纯测试、fixture、harness，除非它本身就是本次要实测的对象；
- 中间态、没跑通、还在等别的 agent 的改动；
- 只为“看看效果”而部署一次小改动。

## 2. 什么时候值得部署

满足任一即可：

1. **有明确用户可见/行为变化**，且自测通过；
2. **必须用真实客户端/真实上游做实测**（本地 fake 不够）；
3. **验收门需要生产构建**（如 A/B、在线复验）；
4. **紧急问题修复**，不部署会阻塞使用；
5. 一批相关改动已经收口，合并成一次部署比多次小部署更合理。

## 3. 部署前最低检查

```text
[ ] 知道这次为什么部署（一句话）
[ ] 对应哪个验收门/功能
[ ] 全量 npm test 0 fail
[ ] 关键定向测试通过
[ ] 工作树干净
[ ] 不是纯 docs/tests-only
```

不要求每次等“完美批次”。  
如果现在就需要真实环境验证，部署是合理成本，不要为了省额度耽误实测。

## 4. 部署后

- 立刻 `GET /healthz` 核对 commit/buildHash；
- 跑本次目标对应的真实检查；
- 记录 `docs/DEPLOYMENTS.md`；
- 如果这次部署没有验证价值，下次就不要为同类小改动再部署。
